The story in 60 seconds

The sales KPI changed: each month an agent must sell more than 15,000 baht in premium and more than five new policies. Three failed months in a row move them to a commission-only contract, and three passes move them back to salary. My design stores one row per agent per month with the result and the running pass and fail streaks, so each month's decision needs only the previous month. Rules are stored as data, so the next KPI change needs no code change, and every contract change is kept in a history table. I built it in SQL and checked it against a separate Python version on thousands of random cases. They agree exactly, and the check even caught a bug with mid-month hires.

Slide 2

The business problem

~1 min
$state_svg
How to read the diagram
  • The two boxes are the two states an agent can be in: SALARY or COMMISSION.
  • The top arrow (SALARY → COMMISSION) fires after 3 consecutive fails; the bottom arrow (back to SALARY) fires after 3 consecutive passes.
  • Anything else leaves the agent where they are. A change becomes effective on the 1st of the next month.
Key point

The rule creates three data needs: a monthly result, a memory of consecutive months (streaks), and a history of contracts. Every table in the design answers one of these.

Here's the rule from the brief. Each month an agent passes if they sell more than 15,000 baht of premium and more than five new policies. Three fails in a row and they move to a commission-only contract; three passes in a row and they move back to salary. It's really a small state machine. So the data model has to record a result every month, remember streaks, and keep the contract history.
Is it AND or OR?
AND: both conditions must hold. The brief says "premium > 15000 & new policy > 5 = Pass". I also store each condition separately, so the rule could be changed to OR without losing information.

The brief didn't say everything, so I made six assumptions and stated them. For example, I treat the thresholds as strict, because the brief says "greater than", so exactly 15,000 is a fail; cancelled policies don't count; and a contract change starts on the first of the next month. Each one is a single setting, so the business can change any of them easily.
Why wouldn't resetting streaks on a contract change matter?
A switch happens at streak 3. After switching to commission, the agent needs passes, and the first pass resets the fail streak anyway. Since a change only triggers when it actually changes the contract, a long fail streak on commission does nothing. The outcome is identical either way.
Slide 4

Design overview

~1 min
What each table is for
  • agent: who the agent is and their current contract (a shortcut copy for quick lookup).
  • policy: every sale. This is the raw input; the KPI is calculated from it.
  • kpi_rule: the thresholds (15,000 · 5 · 3 months) as data, with effective dates.
  • agent_monthly_kpi: the core, one row per agent per month with the result, streaks and decision.
  • agent_contract_history: one row per contract period, recording when it started and ended and why.
  • v_agent_kpi_status: a view (a saved query, not stored data) giving each agent's latest position.
"Grain"

The grain of a table is what one row represents. Saying the grain out loud is the clearest way to explain a design.

There are five tables, each with one job. Agent and policy are the inputs. Kpi_rule holds the thresholds as data. The core is agent_monthly_kpi: one row per agent per month. Contract history keeps every change. On top there's a view for reporting. The key idea is that each monthly row carries the running streaks, so deciding a contract change only needs last month's row.
Why keep current_contract_type on agent if history has it?
It's a deliberate denormalisation for fast lookups ("what contract is this agent on now?"). The monthly job updates it in the same transaction, so it can't drift. History stays the source of truth for any past date.

ER diagram

~1 min
$erd
How to read it
  • Each box is a table: the header is the name, then its columns. PK = primary key (unique row ID); FK = foreign key (points to another table).
  • Arrows go from parent to child. 1 : N = one parent row, many child rows (one agent has many policies, monthly results and contract periods; one rule is used by many monthly results).
  • 1 : 0..1: a monthly result triggers at most one contract change.
  • agent_monthly_kpi has a composite primary key (agent_id + kpi_month): one row per agent per month, enforced by the database.
  • The diagram is generated from the real database, so it can't drift from the SQL.
This is the ER diagram. The agent is the centre: one agent has many policies, many monthly results and many contract periods. Each monthly result points to the rule it was judged by, and when a result triggers a change, the history row points back to it. So for any contract change I can trace exactly which month and which numbers caused it.
Why a composite key instead of a surrogate ID on agent_monthly_kpi?
The natural key (agent, month) is exactly the business rule "one result per agent per month". Making it the primary key lets the database reject duplicates, for example if the job is accidentally run twice.

Boundary rows (agent $sample_boundary_code): why there are two separate pass flags
$sample_kpi_boundary

Exactly 15,000 THB fails the premium condition; exactly 5 policies fails the count condition. The flags show which one failed.

This is one agent through eight months. Three fails in a row and the April row says "to commission". The history table opens a commission contract from the first of May and points back to April as the reason. Three passes later, July's row says "to salary", and she's back on salary from August. So any question like "why was I moved?" is answered by one history row and the monthly row it points to.
The streak keeps counting after the switch (pass streak 4 in August). Is that a problem?
No. The switch only fires from the opposite contract (salary + 3 fails, or commission + 3 passes), so a long streak can't trigger a second change. If the business wants a "fresh start" after a change, it's one CASE expression.
Why both contract_type_before and contract_type_after?
Before is the contract the agent was judged under that month; after is what applies from next month. Keeping both makes each row self-explanatory without joining the history table.

~1 min
The four groups of columns
GroupColumnsQuestion it answers
Measuredtotal_premium, new_policy_countWhat did the agent sell?

Streaksconsecutive_pass, consecutive_failHow many months in a row? How close to a change?

This is the table I'd defend most. One row tells the whole story: what the agent sold, whether each condition passed, how long their streak is, and what we decided. The separate pass flags matter, because a manager wants to know whether the agent missed on premium or on number of policies. And because the streak is stored, I can see that an agent is one month away from losing their salary contract.
Couldn't you compute streaks with window functions instead of storing them?
Yes, streaks can be derived with a "gaps and islands" window query. I store them because the decision is made month by month and must be auditable as it was at the time. Stored values also make the monthly job a simple step that doesn't re-scan history. Since they're derived, they can always be rebuilt from policy data if needed.
Why both is_pass and the two condition flags?
is_pass is what the rule uses; the condition flags explain it. Storing the result rather than recomputing it also keeps history correct if a rule changes later.
Slide 9

Monthly process

~1.5 min
The four steps
  1. Evaluate: for every agent employed in the month, sum the premium and count the new policies (excluding cancelled ones), then compare with the rule whose dates cover the month.
  2. Streaks: read last month's row. On a pass, consecutive_pass = previous + 1 and consecutive_fail = 0; on a fail, the reverse.
  3. Decide: SALARY and fail streak ≥ 3 → TO_COMMISSION; COMMISSION and pass streak ≥ 3 → TO_SALARY; otherwise NONE.
  4. Apply: set effective_to on the old contract, insert the new contract from the 1st of next month, update agent.current_contract_type.
Safeguards (explain why each matters)
  • One transaction: if anything fails midway, nothing is saved, so we never have a result without its contract change.
  • No double run: running April twice would double-count streaks; it's blocked in code and by the primary key.
  • No skipped month: running June before May would break the streak chain, so it's blocked.
Effective dating

effective_to is exclusive (a contract ending 2026-05-01 was in force until 30 April). That makes "which contract was in force on date X" a simple from ≤ X < to check with no gaps or overlaps.

Once a month, after month-end, one SQL job runs in four steps: evaluate, update streaks, decide, apply. Everything runs in a single transaction, so it's all or nothing, and the engine refuses to run a month twice or out of order, because either would corrupt the streaks.

Edge cases

~45 s

Purpose: show you thought about what breaks systems in real life. Pick 2–3 to mention; don't read the whole table.

  • Boundaries (exactly 15,000 / exactly 5) are where rules usually get implemented wrong.
  • No sales: an agent who sells nothing must still fail; otherwise the worst performers escape evaluation.
  • Mid-month hire: found by the verification (slide 13).
  • Re-runs and skipped months: operational mistakes, blocked by the engine.
I wrote a test for every tricky case: the exact boundary values, an agent with no sales, cancelled policies, a broken streak, an agent who keeps failing on commission, mid-month hires, and running a month twice or out of order. All 25 tests pass.
Slide 13

Verification

~1 min
The idea

I implemented the same rules twice: once in SQL (the production job) and once in plain Python (ReferenceKpiEngine), written separately. Both run on the same input and every output column is compared.

The numbers
  • $v_scen demo agent-months + $v_rand_rows agent-months across $v_rand random portfolios, with result $v_result.
  • The random portfolios include mid-month hires, agents who leave, and about 10% cancelled policies.
  • 25 automated tests: business rules, safeguards and SQL-vs-Python equivalence.
The bug it found (tell this story: panels love it)

The first SQL version looked up the contract "in force on the 1st of the month". An agent hired on 15 March had no contract on 1 March, so the SQL silently dropped them from March, while the Python version included them. The fix: use the contract in force at any point during the month. A test now covers it.

To prove the logic is right, I wrote it twice: once in SQL and once, separately, in Python. On over 7,000 random agent-months they agree on every value. This actually caught a real bug: agents hired mid-month were being skipped in their first month. That's exactly the kind of error that would reach payroll unnoticed, and it's now fixed and tested.
Couldn't both implementations share the same mistake?
They could if I misunderstood the rule itself, which is why the assumptions are stated explicitly for the business to confirm. But they can't share an implementation bug, because they're written in different languages with different logic (set-based SQL vs a row-by-row loop).

Reporting view

~45 s
What the view returns

For each agent: the current contract, the last evaluated month and result, both streaks, months_to_change (3 minus the relevant streak) and a status:

  • AT RISK: on salary with at least one fail in a row. months_to_change = fails left before switching.
  • RECOVERING: on commission with at least one pass in a row.
  • STABLE: otherwise.
$status
Heads-up: in the demo, every agent happens to be STABLE after August (A003 and A004 are on commission with a fail streak, so they're stable on commission). If asked, the AT RISK case is covered by a unit test: a salary agent with 2 fails shows AT RISK with 1 month to change.
For the business I added a view that answers the question managers actually ask: who is about to lose their salary contract? One simple query lists agents at risk and how many months they have left, which makes it a coaching tool, not just a record.
Slide 15

Extensibility & next steps

~45 s
  • Rule changes: insert a new kpi_rule with effective_from and close the old one. Each monthly row stores its rule_id, so history stays correct.
  • Scale: about 24,000 rows a year for 2,000 agents, which is trivial for any database. Indexes are on (agent_id, issue_date) for policy and (agent_id, kpi_month) via the primary key.
  • Portability: standard SQL; SQLite is used only for the demo.
  • Next: early-warning alerts at fail streak 2, a re-run procedure for late cancellations, an HR/payroll feed, and a manager dashboard.
The design is built to change. When the KPI changes again, it's a new rule row, not new code. It scales easily. And the natural next steps are early-warning alerts, handling late cancellations, and connecting it to payroll.

Glossary

GrainWhat one row of a table represents (e.g. one agent in one month).
Primary key (PK)Column(s) that uniquely identify a row. Composite PK = more than one column.
Foreign key (FK)A column that must match a row in another table (e.g. policy.agent_id → agent).
Surrogate keyAn artificial ID (1, 2, 3…) with no business meaning.
1 : N relationshipOne parent row relates to many child rows.
DenormalisationDeliberately storing a copy of data (e.g. current contract on agent) for speed.
ViewA saved query that behaves like a table but stores no data.
TransactionA group of changes that is saved all together or not at all.
Effective datingStoring effective_from / effective_to so the value on any date can be found.
SCD type 2Slowly changing dimension: keep a new row per change instead of overwriting. Contract history works this way.
StreakNumber of consecutive months with the same result.
Gaps and islandsA SQL pattern for finding consecutive runs with window functions.
IdempotentSafe to run twice with the same result. The job is protected from double runs instead.
Reference implementationA second, independent version used to check the first.

Tough questions bank

What if a policy is cancelled after the month was already evaluated?
Results are monthly snapshots, so they don't change silently. Two options: (1) evaluate after the free-look or cancellation window (e.g. on the 15th of the next month), or (2) a controlled correction that deletes results from the affected month onwards and re-runs them in order, because later streaks depend on it. Contract history is then corrected and logged.
What if the rule changes in the middle of a month?
The job picks the rule whose effective dates cover the start of the month, so a mid-month change applies from the next month. That's simplest for agents to understand, but the business could choose otherwise.
What if a policy is shared by two agents?
The brief implies one agent per policy. For splits I'd add a policy_agent bridge table with a split percentage and sum premium × share.
Does a newly hired agent start on salary?
The initial contract is whatever HR assigns; it's stored as the INITIAL history row. A probation rule (e.g. no evaluation in the first 3 months) could be added as a column on kpi_rule.
What about an agent who leaves?
termination_date stops evaluation after they leave; their history stays for audit.
Why SQLite?
Only for a self-contained demo. The SQL is standard and moves to PostgreSQL, SQL Server or Oracle with minor syntax changes (e.g. date functions).
How would you schedule it?
A monthly job (Airflow, cron or the database scheduler) runs after month-end close. The engine's checks make a re-run safe to attempt, because it refuses rather than corrupting data.
How do you know your SQL is correct?
25 tests plus an independent Python implementation agreeing on more than 7,000 random agent-months, which found and fixed one real bug.
Should a streak reset when the contract changes?
It gives the same outcome here (explained under slide 3). If the business wants a "fresh start" rule, it's one CASE expression.
Privacy or security?
Agent performance and contract data is HR-sensitive: restrict access by role. The history table already records when and why each contract changed; I would add a changed_by column to record who, for manual overrides.
