1. Requirement

The sales KPI has changed. Agent performance must be validated every month, and the result decides the agent's contract type.

RuleLogic
Monthly passTotal premium > 15,000 THB AND new policies > 5
Fail 3 consecutive monthsContract → commission-based
Pass 3 consecutive monthsContract → salary-based
$state_svg

2. Assumptions

  1. Total premium = sum of premium of new policies issued in the month; cancelled policies are excluded.
  2. Thresholds are strict: exactly 15,000 THB or exactly 5 policies is a fail.
  3. Every agent employed during the month is evaluated. A month with no sales is a fail, so inactive agents cannot avoid evaluation.
  4. A contract change takes effect on the 1st day of the following month.
  5. A change is recorded only when the contract actually changes. A commission agent who keeps failing stays on commission.
  6. Streaks reset only on the opposite result. With rule 5 this gives the same outcome as resetting on a contract change, with simpler logic.

3. Design overview

Core idea: one row per agent per month in agent_monthly_kpi storing the measured values, the pass/fail result and the running pass/fail streaks. Each month needs only last month's row to decide a contract change, and every change is logged in agent_contract_history. Thresholds are data in kpi_rule, so the next KPI change needs no code change.

6. Monthly validation process

Run once per month after month-end with :kpi_month = first day of the month (sql/monthly_kpi_job.sql):

  1. Evaluate: for every agent employed in the month, sum the premium and count new policies, then compare with the rule in force.
  2. Update streaks: on a pass, consecutive_pass = previous + 1 and consecutive_fail = 0; on a fail, the opposite.
  3. Decide: SALARY with consecutive_fail ≥ 3 → TO_COMMISSION; COMMISSION with consecutive_pass ≥ 3 → TO_SALARY.
  4. Apply: close the current contract period, open the new one from the 1st of next month, and update agent.current_contract_type.

Safeguards in the job runner (KpiEngine):

  • All four steps run in one transaction, so a failure leaves nothing half-applied.
  • A month cannot run twice (also enforced by the primary key (agent_id, kpi_month)).
  • A month cannot run before the previous one, because the streaks depend on it.
