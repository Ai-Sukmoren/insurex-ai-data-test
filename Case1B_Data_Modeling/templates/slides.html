Assumptions

Six decisions where the brief was silent

Stated up front so the business can confirm or change them; each one is a single setting in the design

  • Total premium = premium of new policies issued in the month; cancelled policies don't count.
  • Thresholds are strict: exactly 15,000 THB or exactly 5 policies is a fail.
  • Every agent employed during the month is evaluated, and no sales = fail.
  • A contract change takes effect on the 1st of the following month.
  • A change is only recorded if the contract actually changes (no repeated "to commission").
  • Streaks reset only on the opposite result.

InsureX · Test Case 1B8
Monthly process

A four-step job runs once a month, safely

sql/monthly_kpi_job.sql, run with :kpi_month = the first day of the month just closed

1 EvaluateSum premium and count policies for every agent employed in the month; compare with the rule in force.
2 StreaksPass: pass streak + 1, fail streak = 0. Fail: the opposite.
3 DecideSALARY with fail streak ≥ 3 → commission. COMMISSION with pass streak ≥ 3 → salary.
4 ApplyClose the old contract, open the new one from the 1st of next month, update the agent.
Safeguards
  • All 4 steps in one transaction: all or nothing.
  • A month cannot run twice (code check + primary key).
  • A month cannot run before the previous one (streaks depend on it).
Effective dating
  • Contracts use effective_from / effective_to (exclusive).
  • The current contract has effective_to = NULL.
  • Any past date can be answered: "which contract was in force on X?"

Reporting

One query answers "who is about to lose their salary contract?"

The view v_agent_kpi_status shows each agent's latest position and months until a change

Example query for the sales manager
SELECT agent_code, consecutive_fail,
       months_to_change
FROM   v_agent_kpi_status
WHERE  status = 'AT RISK'
ORDER  BY months_to_change;
  • AT RISK: salary agent with ≥ 1 fail in a row; a coaching trigger.
  • RECOVERING: commission agent on a pass streak.

InsureX · Test Case 1B14
Extensibility & next steps

Built to change: new rules, more agents, more uses

What the design already supports, and what I would add next

  • KPI changes again? Insert a new kpi_rule row with an effective date; past months keep their old rule.
  • Scale: 2,000 agents × 12 months = 24,000 rows a year. That's tiny, and indexed on (agent, month).
  • Portable SQL: runs on SQLite for the demo; the same design works on PostgreSQL, SQL Server or Oracle.
  • Early warning: alert agent and manager at fail streak 2.
  • Late cancellations: a controlled re-run from the affected month forward.
  • Integration: feed contract changes to HR and payroll; add a manager dashboard.
