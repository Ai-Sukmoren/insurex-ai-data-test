Opening: the story in 60 seconds

~1 min
I built a sales assistant for InsureX that answers only from the company's product documents and cites the page for every fact. It runs on InsureX's own catalogue: five PDFs built from insurex.co.th, one per product category (health, accident, savings, travel and pet), mostly in Thai. It's a LangGraph state machine: it routes each message, searches a FAISS index, checks that the passages really answer the question, retries once with a better query, and if there's still nothing it says so instead of guessing. When a customer is interested it collects their details and saves a validated lead through an MCP tool, and every chat has its own memory. Everything runs locally. On a 100-question test it scored 91% overall.
2

The brief and how it is covered

~1.5 min
  • Framework: LangChain for models, prompts and splitting; LangGraph for the workflow (state, nodes, conditional edges, a cycle).
  • Vector DB: FAISS, chosen over ChromaDB because it is an in-process library with no server, saved as one file. It is wrapped in my own FaissVectorStore class, so switching is one class.
  • Not-found handling: similarity floor → LLM grader → query rewrite → retry → polite refusal. It never invents an answer.
  • Bonus 1 (lead collection via MCP) and bonus 2 (session memory) are both done; you show them in the demo.
Here's the brief and how I covered it. Everything required is there and I did both bonus tasks. I'll go deeper on three things: how it avoids wrong answers, how the real Thai documents are read, and how leads and memory work.

How the data was collected

Each PDF was generated from insurex.co.th: the product data embedded in the category page, plus the partner product pages it links to. Several of those pages build their content in the browser (the accident plan comparison, the online health, travel and pet pages), so they were loaded in Edge with Playwright, "show more" was clicked until every plan appeared, and the FAQ answers were expanded one by one.

Three reading problems you found and fixed (this is the strongest part of the story)

  1. Thai text was broken. pypdf dropped tone marks and upper vowels ("เบี ย" instead of "เบี้ย"). Switched the loader to PyMuPDF, which reads the text correctly.
  2. Tables fell apart. Each table cell came out on its own line, so a premium lost its row. The loader now joins text that shares a baseline, so "รายปี 36,500 109,500 182,000 362,000" stays one row.
  3. A catalogue mixes many products. A benefit table rarely repeats its product name, so "แผน M 3,000" could belong to any of seven health products. Every chunk is now labelled "document title › section" (e.g. "ประกันสุขภาพ — InsureX › สัญญาเพิ่มเติมคุ้มรักษาพรีม่า แคร์"), taken from the headings and carried over to the next pages.
The documents are InsureX's own catalogue, and reading them well took work. The first PDF library lost the Thai tone marks, tables came out one cell per line, and because each PDF holds many products, a table on its own didn't say which product it was for. I fixed all three in the loader and wrote tests for each.
What if a document is a scanned image?
The loader only reads text layers. I'd add OCR (Tesseract with Thai, or a document-AI service) before chunking; the rest of the pipeline stays the same.

Architecture and the LangGraph flow

~3 min

How to walk through it

  1. classify (LLM, structured output) picks the intent: question, interest, details, recall, decline or greeting. It sees the mode and recent history.
  2. Question path: contextualize (rewrites follow-ups using memory, in Thai, with the Thai product names) → retrieve (top 4, floor 0.45) → grade → generate with citations.
  3. The cycle: if the grader keeps nothing, rewrite_query → retrieve once more, then not_found. The retry counter lives in the state, so it can't loop forever.
  4. Lead path: extract_lead → ask_missing (fields missing) or save_lead (complete, through the MCP server).
  5. Memory: recall answers questions about the chat itself; every turn ends at update_memory, which keeps a running summary.

State (AgentState)

messages (add_messages reducer) · mode (qa / lead_collection, persists across turns) · lead (partial draft) · query, attempts, documents (per turn) · summary, summarized_upto (memory).

This is the heart of it. Every message goes to a router first. Questions take the RAG path: rewrite the question using memory, search, grade, answer with citations. The orange loop is the cycle: if nothing relevant comes back, it rephrases and searches once more before refusing. Interest switches the agent into lead mode, which persists in the state. The badges show which steps call the model; the routing itself is plain Python, which I unit-test.
Why not a ReAct agent that picks its own tools?
A free-form agent is harder to predict and test. Here the LLM classifies, grades and writes, but the control flow is code, so every turn's path is logged and rules like "never answer without relevant passages" are guaranteed.
Why a local model?
Customer income and phone numbers never leave the machine, and there's no per-call cost. The model is one setting (CHAT_MODEL), so a hosted model is a configuration change.

Lessons, next steps, close

~2 min

Lessons (show engineering judgement)

  • Similarity is not relevance. Off-topic questions still get high cosine scores, so a grader and a retry cycle are needed before answering.
  • Real documents break assumptions. Broken Thai extraction, split tables and legacy font encodings were only found by testing on the real PDFs.
  • Chunks need context. A benefit table that never names its product can be mixed up with another product's table. Labelling every chunk with its document and section fixed that class of error.
  • Tune with the test set, not by rule of thumb. Chunk size was picked by running all 100 questions on several settings: 500/100 → 85, 700/120 → 82, 1000/150 → 91, 1200/200 → 89 (see logs/chunk_comparison.md).
  • Measure, then change. Every fix was checked against the same 100 questions, so improvements are numbers, not impressions.

Next steps

  • Build the test set with the sales team, and add LLM-as-judge scoring for answer quality.
  • Hybrid search (BM25 + vectors) and a reranker, which help with exact numbers and plan names.
  • Parse tables into structured rows (or a small SQL table) for premium lookups.
  • Log-in per agent, PDPA consent before collecting details, encrypted leads, CRM integration through the same MCP tool, Docker deployment.
To sum up: a LangGraph agent that answers only from InsureX's documents and refuses when it can't, reads real Thai PDFs correctly, captures validated leads through MCP, remembers each conversation, and runs entirely on the local machine. I'm happy to go into the code or try any question you like.

Tough questions

How do you know the answer is grounded and not right by luck?
Citations are required after each fact, the grader filters passages, and the test checks retrieval and the answer separately. Next I'd add an automatic "is every claim supported?" check.
Why 1000 characters with 150 overlap?
I tested it on these documents. A fast retrieval sweep over 13 settings picked the candidates, then each ran the full 100-question test: 500/100 → 85, 700/120 → 82, 1000/150 → 91, 1200/200 → 89. 1000/150 scored best (91/100, 77/85 answers, 14/15 refusals). Smaller chunks scored lower (85 and 82) and 1200/200 scored 89 with one fewer correct refusal. The likely reason is that at about 1000 characters a benefit-table block stays in one chunk with its plan-name headings; this is an explanation, not something the test measured. Overlap stays at 15% so a fact on a chunk boundary is whole in at least one chunk.
Is 100 questions enough?
It covers every document, both languages, tables and refusals, and every expected answer was checked against the source text. For production I'd grow it with the sales team's real questions and track it on every change.
Why not just put the whole document in the prompt?
Five documents would fit today, but not a real product catalogue. Retrieval keeps prompts small and fast, and citations show exactly where each fact came from.
The accident catalogue has 38 plans. Is RAG the right tool for comparing them?
It works for single lookups ("what does plan 3 cost?"). For "cheapest plan with fracture cover for a 70-year-old" the better design is to load the plan table into a small database and let the agent query it, keeping RAG for the text.
Where did the knowledge base come from?
The brief's PDFs weren't provided, so I built one PDF per product category from insurex.co.th. Pages that load their data in the browser were rendered in Edge with Playwright, and every plan count was checked against the site's own totals.
Can the agent save a lead with wrong data?
It only extracts what the customer typed (the prompt forbids guessing), and the MCP tool rejects invalid phones, empty names and non-positive income. A human agent calling back is the final check.
What about prompt injection inside a document?
The documents are company-controlled; the answer prompt treats context as facts only; the graph, not the LLM, decides the flow; and the only write action uses validated fields.
How would it scale?
FAISS handles millions of vectors (IVF/HNSW index); move the checkpointer to Postgres, run several API workers, serve the model with vLLM or a hosted endpoint. The graph code doesn't change.
What happens if Ollama crashes mid-chat?
The service catches it, returns "the model service is not reachable", logs it, and the session carries on when Ollama is back.
PDPA?
In production: a consent line before collecting details, encrypted leads, retention rules. Deleting a chat already erases its conversation memory.

Glossary

RAGRetrieval-Augmented Generation: find relevant passages first, then let the LLM answer only from them.
Embedding / cosineA vector that represents meaning; cosine similarity measures how close two meanings are (1 = identical).
ChunkA piece of a document (about 1000 characters) that is embedded and retrieved.
GraderAn LLM step that keeps only passages that directly answer the question.
Conditional edge / cycleA transition chosen from the state; a cycle goes back to an earlier node (the retry).
Checkpointer / threadLangGraph saves the state after each step under a thread ID; one thread = one conversation.
MCPModel Context Protocol: an open standard for exposing tools to AI apps (here over stdio).
PUAUnicode Private Use Area: code points a font can use for its own glyphs; old Thai fonts put positioned tone marks there.
เหมาจ่ายLump-sum health cover: one yearly limit for all hospital costs instead of separate limits per item.
DeductibleThe part of a claim the customer pays first; a deductible plan has a lower premium.
