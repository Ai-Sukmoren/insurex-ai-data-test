The story in 60 seconds

I built a sales assistant for InsureX that answers only from the company's product documents and cites the page for every fact. It runs on InsureX's own catalogue: five PDFs built from insurex.co.th, one per product category, mostly in Thai. It's a LangGraph state machine: it routes each message, searches a FAISS index, checks that the passages really answer the question, retries once with a better query, and if there's still nothing it says so instead of guessing. When a customer is interested it collects their details and saves a validated lead through an MCP tool, and every chat has its own memory. Everything runs locally. On a $n_eval-question test it got $n_correct right.

Before you start (10 minutes before)

  • Ollama is running and both models are pulled: ollama list shows $chat_model and $embed_model.
  • Double-click start_chatbot.bat (or python main.py serve) and open http://127.0.0.1:8000.
  • Send one warm-up question, then delete that chat. The first answer loads the model (about 20–30 s); after that answers take a few seconds.
  • Open in tabs: the deck PDF, the web chat, logs/eval_report.md, one PDF from knowledge_base/, and VS Code on src/sales_agent/agent.py (method build) and knowledge_base.py (PdfLoader).
  • Keep this guide on a second screen or printed. Close notifications.

Here's the brief and how I covered it. Everything required is there and I did both bonus tasks. I'll spend the time on three things: how it avoids wrong answers, how the real Thai documents are read, and how leads and memory work. And every number I show comes from a test you can rerun.
Why FAISS rather than ChromaDB?
For $n_chunks chunks both are fine. FAISS needs no server and saves as one file, which suits a local tool. The store is wrapped in one class, so moving to Chroma or pgvector is a small change.

Slide 4

Three problems in the real PDFs, each found by testing and fixed

~1.5 min

Purpose: this is the strongest engineering story. Each problem was found by a failing test question, not guessed in advance.

  1. Thai text broken. pypdf dropped tone marks and upper vowels ("เบี ย" for "เบี้ย"). Switched to PyMuPDF. Old fonts also put positioned tone marks in the Unicode Private Use Area (U+F700–F71A); those are mapped back to standard Thai.
  2. Tables fell apart. Each cell came out on its own line, so a premium lost its row. The loader now joins text that shares a baseline (3 pt tolerance).
  3. Which product is a table for? A benefit table rarely repeats its product name. Every chunk is labelled "document title › section", where the section is the latest heading at least 60% of the title's font size, carried over to following pages. Example: "ประกันสุขภาพ — InsureX › สัญญาเพิ่มเติมคุ้มรักษาพรีม่า แคร์".
Reading the documents well took the most work. The first PDF library lost Thai tone marks, tables came out one cell per line, and because each PDF holds many products, a table on its own didn't say which product it was for. I fixed all three in the loader, and each fix has a unit test.
What if a document is a scanned image?
The loader reads text layers only. I'd add OCR (Tesseract with Thai, or a document-AI service) before chunking; the rest of the pipeline stays the same.
Slide 5

One agent, three stores, everything on the local machine

~1 min

Purpose: the big picture before the graph. Go left to right: two front ends → FastAPI → the agent → three stores.

  • Front ends: React 19 + TypeScript web chat (built with Vite, served by FastAPI, so Node isn't needed to run it) and a command line.
  • Service: FastAPI with REST and server-sent events, so tokens and graph steps stream live.
  • Stores: FAISS (knowledge), SQLite leads behind the MCP server, SQLite checkpointer (memory).
  • Models: Ollama runs $chat_model (chat, tool calling) and $embed_model (embeddings). Both are one setting each.
Customer data never leaves the machine, and there's no per-call cost. The key choice: the model classifies, grades and writes, but the control flow is code. So every turn's path is logged and I can unit-test the rules.
Why a local model?
Privacy (income and phone numbers stay on the machine) and cost. The model is one setting (CHAT_MODEL), so a hosted model is a configuration change.
Why not a ReAct agent that picks its own tools?
A free-form agent is harder to predict and test. Here rules like "never answer without relevant passages" are enforced by the graph, not by hoping the model follows a prompt.
Slide 6

Every message is routed first, then takes one of three paths

~1.5 min
$graph_svg

How to walk through it

  1. classify (LLM, structured output) picks the intent: question, interest, details, recall, decline or greeting. It sees the current mode and recent history.
  2. Blue path, questions: contextualize (rewrites follow-ups using memory, in Thai, with Thai product names) → retrieve (top $top_k, floor $min_rel) → grade → generate with citations.
  3. The cycle: if the grader keeps nothing, rewrite_query → retrieve once more, then not_found. The retry counter is in the state.
  4. Orange path, leads: extract_lead → ask_missing (fields missing) or save_lead (complete, through the MCP server).
  5. Green, memory: recall answers questions about the chat itself; every turn ends at update_memory, which keeps the running summary.

State (AgentState, saved after every step)

messages (add_messages reducer) · mode (qa / lead_collection, persists across turns) · lead (partial draft) · query, attempts, documents (per turn) · summary, summarized_upto (memory).

This is the heart of it. Every message goes to a router first. Questions take the blue path. The orange loop is the cycle: if nothing relevant comes back, it rephrases and searches once more before refusing. Interest switches the agent into lead mode, which is stored in the state, so it keeps collecting details across turns.
What if classify picks the wrong intent?
It uses structured output with a fixed set of intents and, if the output can't be parsed after retries, falls back to "question" (or to "lead details" while collecting a lead). That is the safe path: the worst case is a grounded answer or a refusal.
Slide 7

Similar is not the same as relevant

~1 min

Purpose: explain why a grader is needed, using the recorded car-insurance turn on the slide.

  • Off-topic questions still get high cosine scores against insurance text, so the similarity floor ($min_rel) alone can't detect them.
  • The grader keeps only passages that directly answer. If none survive, one rewritten query, then a polite refusal that says what InsureX does offer.
  • The recorded path on the slide shows the retry: $nf_path.
The classic RAG failure is answering from text that is similar but not relevant. A car insurance question scores high against accident insurance text. So the grader checks the passages first; if nothing fits, it tries one better query, and then it refuses. It never makes up a product.
How do you know answers are grounded and not right by luck?
Citations are required after each fact, the grader filters passages, and the test scores retrieval and the answer separately. Next I'd add an automatic "is every claim supported?" check.

Slide 9

Bonus 1: interest turns the chat into lead capture

~1 min

Purpose: show multi-turn collection and that validation happens in the tool.

  • The lead mode is stored in the graph state. If the customer asks a product question in the middle, it is answered, and the missing fields are asked for again.
  • extract_lead uses structured output into a Pydantic LeadDraft, and the prompt forbids guessing values the customer didn't type.
  • The MCP server (save_lead, list_leads, stdio transport) validates again with the Lead model: Thai phone normalised to 0XXXXXXXXX, positive income, trimmed name. Invalid data returns {"ok": false, "errors": [...]}, and the agent asks again.
  • Recorded demo: $n_leads leads saved (in English and in Thai), one after a rejected phone.
When a customer shows interest, the agent switches into lead mode and collects four details over as many turns as it takes. The checks live inside the MCP tool, not just in the prompt, so any client that calls the tool gets the same data integrity. Here the phone "12345" was rejected and asked for again.
Why MCP and not a plain Python function?
MCP is a standard interface: the same tool can be used by this agent, Claude Desktop or a CRM bot without rewriting it, and validation travels with the tool.
Can it save a lead with wrong data?
It only extracts what the customer typed, and the tool rejects invalid phones, empty names and non-positive income. A human agent calling back is the final check.
Slide 10

Bonus 2: each customer gets a separate memory that survives restarts

~1 min

Purpose: show isolation, persistence and that long chats stay cheap. All three quotes on the slide are from the recorded demo.

  • LangGraph's SQLite checkpointer saves the state after every step under thread_id = session_id.
  • The last $window messages go to the LLM each turn. After $summarize_after unsummarised messages, older ones are folded into a running summary by the update_memory node; the last $keep_recent stay verbatim.
  • The recorded demo closes and re-creates the whole assistant before Alice's last question, to prove memory comes from disk.
Each chat is its own thread. Alice's chat remembers her name and her first question; Bob's chat knows nothing about her. After a full restart, Alice's chat carries on. For long chats, older messages are summarised, so the prompt stays small.
What happens when a chat is deleted?
Its checkpoint thread is erased, so the memory is gone. Saved leads are kept, because they are business records, not conversation memory.

More tough questions

Why not just put the whole document in the prompt?
Five documents would fit today, but not a real catalogue. Retrieval keeps prompts small and fast, and citations show exactly where each fact came from.
What about prompt injection inside a document?
The documents are company-controlled; the answer prompt treats context as facts only; the graph, not the LLM, decides the flow; and the only write action uses validated fields.
How would it scale?
FAISS handles millions of vectors (IVF/HNSW index); move the checkpointer to Postgres, run several API workers, serve the model with vLLM or a hosted endpoint. The graph code doesn't change.
What happens if Ollama crashes mid-chat?
The service catches it, returns "the model service is not reachable", logs it, and the session carries on when Ollama is back.
PDPA?
In production: a consent line before collecting details, encrypted leads, retention rules. Deleting a chat already erases its conversation memory.
How long did the test take to run?
About 12 minutes for $n_eval questions on one local GPU, which is why the chunk comparison used a fast retrieval-only sweep first.

Glossary

RAGRetrieval-Augmented Generation: find relevant passages first, then let the LLM answer only from them.
Embedding / cosineA vector that represents meaning; cosine similarity measures how close two meanings are (1 = identical).
ChunkA piece of a document (about $chunk_size characters) that is embedded and retrieved.
GraderAn LLM step that keeps only passages that directly answer the question.
Conditional edge / cycleA transition chosen from the state; a cycle goes back to an earlier node (the retry).
Checkpointer / threadLangGraph saves the state after each step under a thread ID; one thread = one conversation.
MCPModel Context Protocol: an open standard for exposing tools to AI apps (here over stdio).
PUAUnicode Private Use Area: code points a font can use for its own glyphs; old Thai fonts put positioned tone marks there.
เหมาจ่ายLump-sum health cover: one yearly limit for all hospital costs instead of separate limits per item.
DeductibleThe part of a claim the customer pays first; a deductible plan has a lower premium.
