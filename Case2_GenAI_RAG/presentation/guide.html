The story in 60 seconds

I built a sales assistant that answers questions only from InsureX's product documents and cites the page every time. It's a LangGraph state machine: it routes each message, searches a FAISS index, uses the LLM to check the passages really answer the question, retries once with a better query, and if there's still nothing it says so instead of making something up. When a customer says they're interested, it switches into lead mode, collects their name, job, income and phone over several messages, and saves them through an MCP tool that validates the data. Every chat has its own memory, including a running summary for long conversations, and it all runs locally on Ollama, with a React web chat that shows the agent working step by step. On my test set it found the right document every time, answered all 16 answerable questions correctly and refused both off-topic ones.

Live demo script (3–5 minutes)

Before the interview: start Ollama, run start_chatbot.bat, and send one warm-up question. The first answer loads the model and takes about 30 s; after that, answers take 2–7 s. Keep the browser on New chat.
  1. "How much does PA Plus Gold cost per year?" Point at the streaming answer, the source chip, and the Agent pipeline panel lighting up: classify → contextualize → retrieve → grade → generate → update_memory.
  2. "And how much does it pay for medical expenses?" This shows memory: "it" is resolved to PA Plus Gold.
  3. "Do you sell car insurance?" Point at the orange retry loop (rewrite_query → retrieve) and the safe fallback.
  4. "I'm interested, can an agent call me?" The lead badge appears and the progress ring starts at 0/4.
  5. "I'm Mai, a nurse, 30,000 a month, phone 12345" The phone is rejected by the MCP tool's validation. Then send "sorry, 081-234-5678": the lead is saved, a toast appears, and it shows in Saved leads.
  6. Click New chat and ask "What's my name?" The new chat has no memory of Mai, which shows session separation. Click back to the first chat: the history is still there.
  7. Hover the first chat in the sidebar and click delete. Explain that this erases its memory, while the saved lead stays.
If something goes wrong live: show logs/demo_transcript.md or slide 10. The demo is reproducible with python main.py demo.

The brief

~1 min

Purpose: show completeness. Go down the table quickly; the next slides go deeper.

  • Framework: LangChain for models, prompts and splitting; LangGraph for the workflow (state, nodes, conditional edges, a cycle).
  • FAISS was chosen over ChromaDB: it's a lightweight library with no server, fast, and the index is saved to disk.
  • Both bonus tasks are done: MCP lead collection and session memory.
Here's the brief and how I covered it. Everything required is there, and I did both bonus tasks. I'll go through the interesting parts: how it avoids wrong answers, how lead capture works through MCP, and how memory works.
Why FAISS and not ChromaDB?
For 5 documents, FAISS is the simplest: an in-process library with no extra service, saved as one file. I wrapped it in my own FaissVectorStore class (cosine similarity on normalised vectors), so switching to Chroma means replacing one class.

Architecture

~1 min
  • Left: three ways in: the web chat (React, streaming), the CLI, and tests. All of them use the same service.
  • Middle: SalesAssistant (service layer: sessions, streaming, locks, error handling) wraps the LangGraph agent.
  • Right: four local services: Ollama ($chat_model) for language, FAISS + $embed_model for search, an MCP server writing leads to SQLite, and the SQLite checkpointer for memory.
The architecture has three layers. The front ends, a web chat and a command line, all go through one service class. That service runs the LangGraph agent, which uses four local components: the Ollama model, the FAISS index, an MCP server for leads, and a SQLite checkpointer for memory. Nothing leaves the machine, which matters because we're handling customers' incomes and phone numbers.
Why a local model instead of GPT or Claude?
Privacy and cost for a demo with personal data. The model is a setting (CHAT_MODEL), and the graph doesn't depend on the provider, so moving to a hosted model is a configuration change if the bank allows it.
Slide 4

Knowledge base

~1 min
  • Pipeline: pypdf extracts text per page → RecursiveCharacterTextSplitter ($chunk_size characters, $chunk_overlap overlap, splitting on paragraphs first) → $embed_model embeddings (1024 dimensions) → FAISS inner-product index on normalised vectors, which equals cosine similarity.
  • Retrieval: top $top_k chunks with a similarity floor of $min_rel, then the LLM grader.
  • Sample documents: be upfront that the 5 PDFs are fictional samples, because the real ones weren't provided. Replacing them is python main.py ingest.
Ingestion is one command: read the PDFs page by page, split them into overlapping chunks, embed them with bge-m3 and store them in FAISS. I chose bge-m3 because it's multilingual: a question in Thai finds the answer in an English document. The real five PDFs weren't in the files I received, so I created sample documents. Swapping in the real ones is just re-running ingest.
How did you choose the chunk size?
Around 700 characters keeps one product rule or one table section together, and the overlap prevents a fact being cut in half. With the real documents I'd tune it on the evaluation set.
What if the real PDFs are scanned Thai documents?
pypdf only reads text layers, so I'd add OCR (e.g. Tesseract with Thai, or a document AI service) before chunking. The rest of the pipeline stays the same.
Slide 5

LangGraph design (the most important slide)

~2 min
$graph_svg
How to walk through it
  1. classify (LLM, structured output) picks the intent: question, interest, details, recall, decline or greeting. It sees the mode and recent history.
  2. Question path: contextualize (rewrites follow-ups using memory) → retrieve → grade → generate. If grading finds nothing, it takes the cycle: rewrite_query → retrieve again (max $top_k chunks, 1 retry), then not_found.
  3. Lead path: extract_lead → ask_missing (fields missing) or save_lead (complete, via MCP).
  4. Memory: recall answers questions about the chat itself. Every turn ends at update_memory, which maintains the running summary.
State (AgentState)

messages (add_messages reducer) · mode (qa / lead_collection, persists across turns) · lead (partial draft) · query, attempts, documents (per turn) · summary, summarized_upto (memory).

This is the heart of it. Every message first goes to a router. Questions go through the RAG path: rewrite the question using memory, search, grade, answer. The orange loop is the cycle: if nothing relevant comes back, it rephrases and searches once more before giving up safely. Interest switches the agent into lead mode, which persists in the state, so the next message is understood as details. And every turn ends by updating memory. The LLM badges show which steps call the model; the routing decisions themselves are plain Python functions, which I unit-test.
Why not a ReAct agent that decides which tool to call?
A free-form agent is harder to predict and test. Here the flow is explicit: the LLM classifies, extracts and writes, but the control flow is code. That makes behaviour auditable (every turn logs its path) and lets me guarantee rules such as "never answer without relevant passages".
How do you prevent infinite loops?
The retry counter (attempts) is in the state and capped by max_query_rewrites = 1, and the graph also has a recursion limit of 25.
Slide 6

Precision and error handling

~1.5 min
  • The bars: top cosine similarity for three questions. "Car insurance" (0.52) scores almost like real questions (0.58–0.61), so no threshold can separate them.
  • The grader sees the numbered passages and returns which ones directly answer. It's told explicitly that a list of other products doesn't answer a question about car insurance.
  • Safe defaults: if the model's structured output fails, the grader defaults to "nothing relevant" → retry → fallback. Wrong refusals are better than invented answers.
  • Grounding: the answer prompt allows only context facts, requires a citation after each fact, and must say which part wasn't found.
This is how I keep precision high. The vector search always returns something, and as you can see, an off-topic question like car insurance scores almost as high as a real one. So I added a grading step where the model checks whether each passage really answers the question. If nothing does, it rephrases and tries once more, and then it politely says it couldn't find the information. On my test set it refused both off-topic questions and answered all 16 real ones.
Doesn't the grader add latency and cost?
One short extra call per question, about 0.5–1 s locally, and no money. It's the step that prevents wrong answers, so it's worth it. For scale, a cross-encoder reranker could replace it.
Slide 7

Bonus 1: lead collection with MCP

~1.5 min
  • Trigger: the router detects interest ("I'm interested", "สนใจ", "I'd like to apply") → mode = lead_collection.
  • Extraction: the LLM fills a Pydantic LeadDraft (all fields optional) from the customer's messages since lead mode started. Values merge across turns, so details can come in any order.
  • MCP: mcp_server.py is a standard Model Context Protocol server (FastMCP, stdio) with save_lead and list_leads. The agent calls it through langchain-mcp-adapters, and any MCP client could use it.
  • Data integrity: validation happens inside the tool (Pydantic Lead): Thai phone format normalised to 10 digits, income > 0, names trimmed. A rejected field is cleared and asked again; valid fields are kept.
  • Side questions in the middle of collection are answered, then the agent reminds the customer what's still missing.
When a customer shows interest, the agent switches into lead mode. It extracts the four fields into a Pydantic model, asks only for what's missing, and when everything is there it calls an MCP tool to save the lead. I put the validation inside the tool, so any client gets the same data quality. In the example, Dave gives an invalid phone, the tool rejects it, the agent asks only for the phone again, and then saves him as lead number 3.
Why MCP instead of just calling SQLite from Python?
The brief asked for it, and it decouples the agent from the storage. The same tool could point to the real CRM, be used by other agents, or be tested with the MCP Inspector, and the agent code wouldn't change.
What about consent and PDPA?
In production I'd show a consent line before collecting details, encrypt the leads table, and add retention rules. Deleting a chat already removes its conversation memory.
Slide 8

Bonus 2: session memory

~1.5 min
  • Checkpointer: LangGraph's AsyncSqliteSaver stores the full state after each node, keyed by thread_id = session_id. That gives separation (one thread per chat) and persistence (survives restarts).
  • Efficient recall: prompts get the last $window messages, not the whole history. Once more than $summarize_after messages are unsummarised, update_memory folds the older ones into a running summary (keeping the last $keep_recent verbatim). Prompts get summary + recent messages.
  • Session management: a server-side index (SessionIndex) lists chats with title, date and message count; rename; delete erases the thread's checkpoints.
  • Concurrency: one async lock per session, so two tabs can't interleave the same conversation.
For memory, each chat is a separate LangGraph thread saved in SQLite. That gives separation, because Bob can't see Alice's chat, and persistence, because you can close the app and continue later. To stay efficient, the model only sees the most recent messages plus a running summary of older ones, which a dedicated node keeps up to date. I tested it with a long chat: after 14 messages, the agent still knew the customer was a pharmacist and could repeat the first price it had quoted.
Why not send the whole history every time?
Long histories slow the model, can overflow the context window, and dilute attention. The summary keeps facts that matter (name, products, prices) at a fixed cost.
What does "delete" really delete?
All checkpoints of that thread (the memory) and its index entry. Leads that were already saved are business records, so they stay; that's a deliberate choice I'd confirm with compliance.

Code quality

~45 s
  • OOP, one job per class: loader, chunker, vector store, knowledge base, agent (graph), service, session index, lead models, repository, MCP server and client, demo runner, evaluator.
  • Configuration: one Settings dataclass, overridable by environment variables; all prompts in prompts.py.
  • Error handling: structured-output fallback chain; a turn never crashes; friendly message if Ollama is down; validated API inputs.
  • Tests: $n_tests, including MCP over a real stdio connection, the web API with a fake agent, and an end-to-end test that runs only when Ollama is available.
The code is organised as small classes with one job each, configuration is in one place, and every failure path returns a friendly answer instead of crashing. There are $n_tests tests, including one that talks to the MCP server over a real connection.
Slide 13

Lessons learned

~1 min

Purpose: show engineering judgement. Panels value candidates who test, find problems and fix them.

  1. Similarity isn't relevance, so I added the grader and the retry cycle.
  2. Local structured output is fragile: JSON-schema mode dropped fields; tool calling sometimes skipped the call (88% accuracy). A retry and fallback chain reached 100%.
  3. Routing edge case: a self-introduction started lead collection. The first fix then broke a Thai "interested + details" message in the demo, which led to the final rule: details count as a lead only after interest, or when a phone number is given.
Three things went wrong during development, and each one was caught by the evaluation or the demo, which is exactly why I built them. The big lesson: with LLM systems, you need a test set and a replayable demo to change anything safely.

Glossary

RAGRetrieval-Augmented Generation: search relevant passages first, then let the LLM answer from them.
EmbeddingA vector of numbers representing a text's meaning; similar texts have similar vectors.
Cosine similarityHow closely two vectors point the same way (1 = identical meaning).
ChunkA small piece of a document (here about 700 characters) that is embedded and retrieved.
FAISSFacebook AI Similarity Search: a library for fast vector search.
LangGraphA library for building LLM workflows as graphs: nodes (steps), edges (transitions) and a shared state.
Conditional edgeA transition chosen by a function of the state (e.g. "relevant passages? → generate, else rewrite").
CycleAn edge back to an earlier node (rewrite_query → retrieve), allowing a retry.
ReducerHow a state field is updated; add_messages appends new messages instead of replacing them.
Checkpointer / threadLangGraph saves the state after each step under a thread ID; one thread = one conversation.
MCPModel Context Protocol: an open standard for exposing tools and data to AI applications over stdio or HTTP.
PydanticA Python library for typed data models with validation.
Structured output / tool callingMaking the LLM return data that fits a schema, either by "calling a tool" with arguments or by JSON mode.
Grounding / hallucinationGrounded = based on the sources; a hallucination is a confident answer that isn't in the sources.
SSEServer-sent events: a one-way HTTP stream from server to browser, used for steps and tokens.
OllamaA local runtime for open LLMs (here Qwen3 14B and bge-m3).

Tough questions bank

How would this scale to thousands of documents and users?
FAISS handles millions of vectors (switching to an IVF/HNSW index); move the checkpointer to Postgres, run several API workers, and serve the model with vLLM or a hosted endpoint. The graph code stays the same.
What about prompt injection hidden in a document?
Documents are company-controlled, which limits the risk; the answer prompt treats context as facts only, the graph controls the flow (the LLM can't call tools freely), and the only write action, saving a lead, uses validated fields.
How do you know the answer is grounded and not just correct by luck?
Citations are required after each fact; the grader filters passages; and the evaluation checks retrieval and answer separately. Next I'd add an automatic "is every claim supported?" check.
Why Qwen3 14B?
The best tool-calling model that fits in 12 GB of VRAM here, and it handles Thai. Thinking mode is turned off for speed. Smaller models work via the CHAT_MODEL setting, at some accuracy cost.
Why a separate grader instead of asking the generator to refuse?
Separation of concerns: a small yes/no decision is more reliable than asking one prompt to judge and write at once, and it lets the graph branch (retry) instead of just refusing.
What happens if Ollama crashes during a chat?
The service catches it, returns "the model service is not reachable", logs it, and the session stays usable when Ollama is back.
Can the agent save a lead with wrong data?
It can only save what the customer typed (the extraction prompt forbids guessing), and the MCP tool rejects invalid phones, empty names and non-positive income. A human agent then calls the customer, which is the final check.
How is this different from a chatbot with a long system prompt?
Explicit control flow, retrieval with citations, a refusal path, persistent state per session, and a validated write action. Every turn's path is logged and testable.
