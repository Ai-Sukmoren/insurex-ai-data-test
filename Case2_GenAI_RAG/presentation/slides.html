How the PDFs were made

InsureX · Test Case 23
Reading the documents

Three problems in the real PDFs, each found by testing and fixed in the loader

The PDF reader is where most of the accuracy is won or lost

1 · Thai text was broken

pypdf dropped tone marks and upper vowels:

เบี ย instead of เบี้ย (premium)

Fix: switched to PyMuPDF, and mapped legacy font glyphs (Unicode U+F700–F71A) back to standard Thai.

2 · Tables fell apart

Every table cell came out on its own line, so a premium lost its row and its plan.

รายปี 36,500 109,500 182,000 362,000

Fix: text that shares a baseline (within 3 pt) is joined, so a table row stays one line.

3 · Which product is this table for?

A health PDF holds 7 products, and a benefit table rarely repeats the product name. "แผน M 3,000" could be any of them.

Fix: every chunk is labelled "document › section", taken from the headings and carried across pages.
Result: English questions find Thai answers (multilingual $embed_model), and a benefit table stays linked to the right product. Each fix has its own unit test.

Honest limits

The $n_fail misses are mostly table lookups, and each has a clear next step

Every failing question is listed in the presenter guide and in logs/eval_report.md

What goes wrong

  • Wrong column or row in a wide table, e.g. a premium read from the next plan or age band.
  • A number from a neighbouring field, e.g. the premium given when the fracture benefit was asked.
  • Over-cautious refusals on a waiting-period question whose answer was retrieved but not used.

What I would do next

  • Parse tables into rows (or a small SQL table) and let the agent query premiums directly.
  • Hybrid search (BM25 + vectors) and a reranker for exact plan names and numbers.
  • Grow the test set with the sales team's real questions and add an LLM judge for answer quality.
Safety holds even when it misses: wrong cells are the risk, not invented products, and refusals for unknown products held $n_refused/$n_oos.
